# Data: sources, credits and terms

The files in this folder are generated by `updateData.js`, `scripts/collect-servers.js` and
`scripts/collect-social.js` (see `docs/ARCHITECTURE.md` for the formats). Do not edit them by hand.

| File | What it is |
|---|---|
| `mastodon-daily.csv` | The downloadable dataset: one row per archived UTC day since 2022-09-30. The same rows as `historicalData.js` in the repository root (which is what the page loads), plus the reading time of the FediDB counter, the two day-over-day net changes and posts per day. Rewritten by `updateData.js` on every run. |
| `servers.js` | The server data the page loads (`window.MASTODON_SERVERS`): FediDB's totals for Mastodon-software servers, the 100 largest servers, up to 25 rows per server board, the decentralization shares and up to 8 daily snapshots that are the baseline for gainers and losers. |
| `social.js` | The account data the page loads (`window.MASTODON_SOCIAL`): up to 25 rows per account board, each listed account's public profile fields, up to 25 top posts and up to 8 daily follower and post-count snapshots of eligible accounts. |

The data is derived from the sources below and stays under their terms. If you reuse it, credit them.

## `mastodon-daily.csv` columns

Header: `date,total,active,servers,statuses,statuses_at,fedi_users,fedi_instances,net_total,net_active,posts_per_day,flags`.
Days with no row in the archive are simply not in the file (nothing is interpolated). An empty cell
means the source was not read for that day, or (for the derived columns) the value cannot be
computed. A flagged value (see `flags`) is still written in its own column, as the archive holds it;
only the derived columns go blank around it, and the page treats a flagged value as missing.

| Column | Meaning | Source |
|---|---|---|
| `date` | UTC calendar day, `YYYY-MM-DD`. Only complete days are stored: the day the updater runs on is skipped. | joinmastodon.org statistics API (`period`) |
| `total` | Accounts on all servers that report to joinmastodon.org, for that day. The API's `user_count`. Not registrations: it can fall when a server stops reporting or accounts are removed. | joinmastodon.org statistics API |
| `active` | Monthly active users: accounts active in the trailing 30 days. The API's `active_user_count`. A rolling window, not a daily count. | joinmastodon.org statistics API |
| `servers` | Servers that report to joinmastodon.org. The API's `server_count`. Present only for days where a source carried it (first value 2022-12-01; the live API window and the Wayback captures); empty before that and on days without a reading. | joinmastodon.org statistics API |
| `statuses` | FediDB's cumulative count of posts (statuses) on servers running Mastodon software. One reading per row that has one, taken after that UTC day ended, at whatever hour the update ran (see "FediDB readings" below). First reading: the 2026-10-11 row. | FediDB `GET /v1/software/mastodon`, `status_count` |
| `statuses_at` | When that reading was taken: ISO time in UTC to the minute, `YYYY-MM-DDTHH:MMZ`, for example `2026-10-12T05:17Z`. Always on the UTC day after the row's `date`, because the updater attaches a reading only to yesterday's row. It is part of the same reading as `statuses`, `fedi_users` and `fedi_instances`. | recorded by `updateData.js` when it received FediDB's answer |
| `fedi_users` | Accounts on those servers, same reading. A different base from `total` (8.82M against 10.50M on 2026-10-11). | FediDB, `user_count` |
| `fedi_instances` | Mastodon-software servers FediDB knows about, same reading. A different base from `servers`. | FediDB, `instance_count` |
| `net_total` | `total` minus the previous day's `total`. Blank unless the previous calendar day has a row and both values are present and not flagged. Net, not registrations. | derived here |
| `net_active` | The same for `active`. | derived here |
| `posts_per_day` | Posts per day on the page: `(statuses[d] - statuses[prev]) / elapsed days`, where `prev` is the nearest earlier row that has a reading and elapsed is the time between the two `statuses_at` values. Rounded to a whole number in the CSV (the page keeps the unrounded rate). The value belongs to the later row only: after a missing reading it is an average over the longer interval. Blank when either reading is missing or flagged, when fewer than 6 hours separate the two readings, or when the counter fell. A row with `statuses` but no `statuses_at` is taken to have been read at 03:00 UTC on the day after its date. | derived here by `lib/rates.js` |
| `flags` | Metrics whose value that day is treated as unreliable, joined with `\|`: `total`, `active`, `servers`, `statuses` (`statuses` also covers `statuses_at`, `fedi_users` and `fedi_instances`, which are one reading). Empty when nothing is flagged. | computed here by `lib/flags.js` |

### FediDB readings

FediDB reports totals as of the moment it is asked, not per day. The updater asks once per run,
and only when the newest complete day (yesterday, UTC) has no reading yet; the answer goes on that
row together with the time it was read (`statuses_at`), at any hour of the day after. A reading is
never overwritten, and a run does not attach one to an older day. GitHub starts the scheduled runs
hours after their nominal 03:17 and 15:17 UTC (4 to 8 hours late have been observed on this
account), so readings are not at a fixed hour, and that is why posts per day divides by the real
time between two readings instead of assuming 24 hours. A day whose reading was missed has no
reading (a gap), and the next figure then averages over the longer interval.

A reading is rejected, with a log line, when `statuses` is more than 20 percent per elapsed day
above the last stored reading, or below it when that reading is at most 7 days old (a cumulative
count cannot fall). Elapsed time is measured from the last stored reading's `statuses_at`, at
least one hour. A FediDB failure only logs a warning and the day keeps no reading.

The Mastodon-software total is a count of what FediDB has crawled, not of every Mastodon post, and
posts per day is the average rate between two readings, not a count of the posts of one calendar
day.

**The 2026-10-11 row.** It holds the first FediDB reading, and no time was recorded when it was
taken. Its `statuses_at` was set afterwards from a bound: the reading was taken between 05:09 and
05:25 UTC on 2026-10-12, and the stored `2026-10-12T05:17Z` is the midpoint, so it can be off by up
to 8 minutes. Every later reading records its own time.

## Sources and terms

- **[joinmastodon.org statistics API](https://api.joinmastodon.org/statistics)** (`api.joinmastodon.org/statistics`):
  `user_count`, `active_user_count` and `server_count` per UTC day. It returns only the most recent
  30 to 31 days, so the history in this repository was built by reading it regularly since
  2022-09-30 and by the Wayback back-fill below. The API publishes no licence or terms for these
  aggregate counts; they are used with credit. It also revises its own history after the fact
  (see the gap fill below).
- **[FediDB](https://fedidb.com/)** (`api.fedidb.org/v1`, by [@dansup](https://mastodon.social/@dansup)):
  the Mastodon-software totals (`/v1/software/mastodon`) and the server list (`/v1/servers?software=mastodon`,
  40 per page, cursor paged) behind `statuses`, `fedi_users`, `fedi_instances`, `servers.js` and the
  list of servers scanned for `social.js`. No licence or terms were found on fedidb.org (which now
  shows only a notice that it moved to fedidb.com) or fedidb.com on 2026-10-12, so the figures are
  used with credit. The API sends `x-ratelimit-limit: 30`; the collectors wait 3 seconds between
  requests, honour `Retry-After` on a 429 and send a User-Agent that links back to this repository.
- **Each Mastodon server's own public API** (no sign-in, no key): `GET /api/v1/directory`,
  `/api/v1/trends/statuses`, `/api/v1/accounts/lookup`, `/api/v1/accounts/<id>/following` and
  `/api/v1/statuses/<id>` on the 40 largest servers and on the servers of the accounts found there.
  This is the source of `social.js`: handles, display names, avatar links, follower and post counts,
  last-post days, account creation days and post text. Requests are spaced 1.1 seconds apart per
  server, stop for a server that answers 429 with a long wait, and are capped per server and per run
  (see `docs/ARCHITECTURE.md`).
- **[Internet Archive Wayback Machine](https://web.archive.org/)** captures of
  `https://api.joinmastodon.org/statistics`, used once to fill gaps (below). Wayback replays are
  subject to archive.org's [Terms of Use](https://archive.org/about/terms.php).
- Not data, but loaded by the page: [Chart.js](https://www.chartjs.org/) 4.5.1,
  [chartjs-plugin-zoom](https://github.com/chartjs/chartjs-plugin-zoom) 2.0.1 and
  [Hammer.js](https://hammerjs.github.io/) 2.0.8 (all MIT, from jsDelivr), and the fonts IBM Plex Sans
  and JetBrains Mono (SIL Open Font License, from Google Fonts).

## What was changed

- **Day assignment.** The API's `period` is used as the UTC day. The day the updater runs on is
  skipped (it is still being counted), so a row is only stored after its day ended.
- **Outlier guard.** A new API record at least 20 percent below the newest archived `total` or
  `active` is not stored (a partial aggregate), unless the same low level holds for 3 or more
  consecutive API days ending at the newest one (a block of accounts left the sum for good): then
  the days are stored and the run logs it. Days already in the archive are never overwritten by the
  API.
- **Flags.** `flags` marks days on which joinmastodon's sum jumped because a block of accounts
  entered or left the servers its crawler reaches, and the jump reversed or no real event explains
  it. The raw values are kept. Rules and the hand-checked table are in `lib/flags.js`
  (`KNOWN_STEPS`, `ROLLING`); the page and the net columns treat a flagged value as missing. Real
  surges (the Nov 2022 Twitter wave, the Jul 2023 Threads wave) are not flagged.
- **Net changes and posts per day.** `net_total`, `net_active` and `posts_per_day` are computed
  here from stored rows (`updateData.js`, `lib/rates.js`); nothing is added to the archive for
  them.
- **FediDB readings.** One reading is attached to the newest complete day when it has none, whatever
  the hour, with its time in `statuses_at`; it is never overwritten.
- **`servers`.** The updater stores `server_count` for new days and fills it on archived days that
  lack it from the 30 days the API returns. The Wayback captures below also carry it, and it was
  added from them to the 512 archived days that captures cover (the `total` and `active` of those
  rows were not touched).
- **Gap fill.** The 320 back-filled rows below.

## Gap fill (2026-10-12)

Gap fill (2026-10-12). 320 of the 322 UTC days missing from the archive were back-filled from Internet Archive Wayback Machine captures of https://api.joinmastodon.org/statistics (raw form https://web.archive.org/web/<timestamp>id_/https://api.joinmastodon.org/statistics, 87 captures between 2023-05-04 and 2026-08-20; timestamps are listed per gap in scripts/backfill-history.js --report). Each capture holds the 30 to 31 UTC days the API returned at that moment (period, server_count, user_count, active_user_count), the same series the daily updater stores. For each missing day the earliest capture after it was used (first reading; lag 1 to 21 days). Existing rows were never changed. The API revises its history retroactively: of 512 archived days that captures also cover, 32 (6%) differ, nearly all by block-sized steps. Two days, 2022-12-07 and 2022-12-08, are listed by the API itself with zero counts and stay gaps. Nothing is interpolated. The API publishes no licence or terms for these aggregate counts; Wayback replays are subject to archive.org Terms of Use. rattletat/mastodon-statistics was evaluated and not used because it stores the first (still partial) value seen for each day.

Notes on that paragraph, checked against `scripts/backfill-history.js` on 2026-10-12:

- The 14 gaps it closed were 2022-12-07 to 2022-12-08 (left open), 2023-05-02 to 2023-05-18,
  2023-08-16 to 2023-08-19, 2023-10-03 to 2023-10-07, 2023-10-16, 2023-11-16 to 2023-11-21,
  2024-04-04 to 2024-04-06, 2024-07-04 to 2024-07-05, 2025-01-31 to 2025-02-07,
  2025-03-08 to 2025-03-13, 2025-08-09 to 2025-08-10, 2025-09-11 to 2025-09-14,
  2025-10-15 to 2026-06-18 (247 days) and 2026-07-21 to 2026-08-04.
- A back-filled day carries the earliest capture's reading. Because the API revises its history, that
  is not guaranteed to equal what the daily updater would have stored on the day. Some filled days
  are flagged by `lib/flags.js` (for example 2023-11-16 to 2023-11-21).
- The overlap figures were computed from the 136 captures downloaded (of 761 listed with HTTP status
  200 in Wayback's CDX index on that day), not from all of them.
- To see the per-gap capture list again, run the script against the archive as it was before the
  back-fill (the commit before the one that added these rows; `git show <commit>:historicalData.js`
  into a scratch file) with `--hist` and `--report`. It is offline by default and reads
  `.cache/backfill-history/` (git-ignored); pass `--fetch` to download the captures again
  (at most about 10 requests a minute, or archive.org blocks the client).

## What `servers.js` and `social.js` name

`servers.js` names servers (domain names, user counts, post counts, open or closed registration,
software version) taken from FediDB. Server names are public.

`social.js` names accounts: handles, display names, avatar links, follower and post counts, last-post
and creation days, and the text, favourite, boost and reply counts of posts. These are public
Mastodon profile and post data, shown only for accounts with at least 10,000 followers that opted
into discoverability and carry no bot, locked, group, no-index, suspended, limited, moved or memorial
state, and for posts that are public, not marked sensitive and carry no content warning. Avatar links
are taken from the account's own server as given; the page loads them only from an allow-list of
media hosts (`AVATAR_HOSTS` in `lib/social.js`, mirrored in `social.js`). Avatars, display names and
post text belong to the people who wrote them and are not covered by this repository's MIT licence.
If you reuse them, keep the guardrails, and note that a profile or post may have changed or been
deleted since the build.

Accounts below the 10,000-follower line, accounts that did not pass the rules and their follower
histories are never written to a committed file, and the collector keeps no local state between
runs: the only history is the up to 8 daily snapshots inside `social.js` itself, which contain only
eligible accounts.
